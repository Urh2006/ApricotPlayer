# Audit PODDL: Podcasts/RSS + Downloads/Conversion + AudioVault + Updater

Status: COMPLETE

## 1. Summary

The Podcast/RSS feature set (feed list, episode list, categories, Apple directory search, OPML import/export, speed presets, auto-refresh, new-episode notifications, batch episode loading) and the core Downloads flow (single/collection download, confirm/ask-location gating, current-downloads screen, progress dialog) are ported to a high degree of fidelity: focus order, context menu content/order (including a dynamically-swapped "mark played/unplayed" label), keyboard shortcuts, and list row text formats match Python closely, field-for-field, in most screens checked. Two concrete regressions were found in the ported code: the RSS episode list is missing the "queued for download" marker Python shows inline, and the download keyboard shortcut lacks Python's 0.35s duplicate-press debounce (could double-confirm/double-queue on key-repeat). A third, lower-confidence finding concerns audio downloads not being progress-rate-limited the way Python and Rust's own video downloads are, which needs runtime NVDA confirmation. Two large features are essentially unimplemented in Rust and confirmed here from the podcast/downloads angle (both already tracked by other audit agents): the entire AudioVault feature (login, search, remote/cached playback, downloads) and the updater (yt-dlp auto-update, app self-update, changelog, skip-version) — settings/menu entries exist but do nothing. The file/folder converter dialogs are also completely unimplemented (menu entries exist but `activate_action` has no handler and no converter code exists anywhere in the Rust tree), which is new and specific to this audit's area.

## 2. Deviations in ported functionality

### PODDL-01 (P2): Missing debounce on download keyboard shortcut (duplicate downloads on key-repeat)
- Python ref: `apricot/download/download.py:338-357` (`start_download_shortcut`) tracks `self.last_download_shortcut = (kind, url, now)` and, if the same kind+url is requested again within 0.35s, silently ignores it (`if kind == last_kind and url == last_url and now - last_time < 0.35: return`). This guards against NVDA/keyboard users whose key can auto-repeat or who double-press the download shortcut, which would otherwise pop the confirm dialog twice or start the download twice.
- Rust ref: `crates/apricot-ui-windows/src/win32.rs:6966` (`start_active_download`) and `confirm_download` (`win32.rs:7463`) have no time-based debounce; every WM_KEYDOWN for the download shortcut re-enters `start_active_download` → `confirm_download` → potentially a second `MessageBoxW` confirm prompt or a second download task.
- Suggested fix: track the last (kind, url, timestamp) triggered via the shortcut path (not the context menu) in `WindowState` and skip re-invocation within ~350ms, matching Python.

### PODDL-02 (P3, needs runtime verification): Download progress events are not rate-limited for audio downloads
- Python ref: `apricot/download/download.py:554-626` (`make_download_progress_hook`) rate-limits ALL progress reporting (audio and video alike) to at most one UI update per 0.75s unless the percent bucket or title changes (`now - last_reported_at >= 0.75`), both for the status-bar text and for the `download_task` UI-queue message that drives the progress dialog/list.
- Rust ref: `crates/apricot-platform/src/download.rs:408-444` (`append_mode_arguments`) only passes `--progress-delta 0.5` for `DownloadMode::Video` (line 431-432); the `DownloadMode::Audio` branch (lines 414-422) has no `--progress-delta`, so yt-dlp's external CLI process can emit `APRICOT_PROGRESS:` lines much more often than every 0.5-0.75s for audio-only downloads. Each parsed line flows straight through `apply_download_update` (`crates/apricot-ui-windows/src/win32.rs:8089`) into `update_download_progress_window` (`win32.rs:8026`), which calls `SetWindowTextW` on the progress dialog's static text control every time with no additional throttling.
- Impact: for the (very common) "download audio" action, the floating download-progress dialog's message control could update far more frequently than in Python. If NVDA has "report dynamic content changes" on and that control happens to be focus-adjacent, this could produce much chattier announcements than Python's throttled equivalent. The always-visible current-downloads list refresh itself is not announced per-tick in either version (`refresh_download_projection` passes `announce=false`), so the practical impact is likely confined to the progress dialog text, not the main list.
- Suggested fix: add `--progress-delta 0.5` (or match Python's 0.75s) to the audio argument branch too, or throttle in `apply_download_update`/`update_progress` in Rust regardless of mode.
- Needs runtime verification: whether NVDA actually vocalizes the progress dialog's static-text updates while it doesn't have focus, and how often in practice.



## 3. Missing functionality

### PODDL-03 (P2): RSS episode list row is missing the "queued for download" marker
- Python ref: `apricot/library/library.py:1734-1748` (`rss_item_line`) appends `queued = self.t("podcast_audio_queued_marker") if str(item.get("url") or "") in self.download_queue else ""` as the last `" | "`-joined segment, so a screen-reader user browsing the episode list can hear that an episode is already selected/queued for download.
- Rust ref: `crates/apricot-ui-windows/src/win32.rs:4424-4451` (`rss_episode_label`) builds `title | played? | resume? | published? | duration? | podcast_episode` and never checks `state.application.downloads().queued()` (or equivalent) for a matching URL — the `"podcast_audio_queued_marker"` key is only used elsewhere, in `queued_download_label` (`win32.rs:6825-6842`) for the separate Download Queue screen's rows, not for the RSS items list.
- Suggested fix: in `rss_episode_label` (or its caller `refresh_rss_items`), check whether the episode's URL is present in the download queue and append the `podcast_audio_queued_marker` text, matching Python's field order (after duration/type).

### PODDL-M-01 (P1): File converter and folder converter dialogs entirely missing in Rust
- Python ref: `apricot/media/media.py:40-45` (`show_file_converter`, `show_folder_converter`) and the full dialog implementation `show_converter_dialog` (`apricot/media/media.py:104-325`, format choice, audio-to-video options, create-new-file/replace-original checkboxes, ffmpeg invocation via `converter_ffmpeg_args`/`converter_audio_codec_args`/`converter_video_codec_args` at lines 369-436). This lets a user convert a single media file, or batch-convert every media file in a folder, between audio/video formats via ffmpeg, entirely from the keyboard.
- Rust ref: menu/command-palette entries exist (`crates/apricot-core/src/menu.rs:75-80`, `crates/apricot-core/src/screen.rs:165-166`, `crates/apricot-app/src/action_finder.rs:76-77,234`) so "File converter" and "Folder converter" show up in the main menu and command finder, but `activate_action` in `crates/apricot-ui-windows/src/win32.rs:10760` has no match arm for `"file_converter"`/`"folder_converter"` (confirmed via `grep` — no occurrences of either string anywhere under `crates/apricot-ui-windows/src`), and no `*converter*` source file exists in the Rust tree (`find crates -iname "*convert*"` returns nothing). Activating either menu item is therefore a dead click/Enter for a keyboard user — no dialog opens, nothing is announced.
- Note: this overlaps in root cause with the already-documented generic "activate_action() dispatch gaps" finding (audit-SHELL.md), but is called out here specifically because the entire converter feature (not just the dispatch wiring) is unimplemented in Rust — there is no dialog, no ffmpeg argument building, no batch-folder scanning logic anywhere in the Rust codebase to wire up even if the dispatch gap were fixed.
- Suggested fix: implement a converter dialog (modal, Win32 native) mirroring Python's form fields and ffmpeg argument construction, then add the `"file_converter"`/`"folder_converter"` arms to `activate_action`.

### PODDL-M-03 (P1, cross-referenced with audit-SHELL.md "app self-update" and audit-SETTINGS.md "settings command buttons stubbed"): Updater feature is almost entirely unimplemented
Confirmation-only per instructions (not a re-audit of the already-known findings).
- What exists in Rust: `crates/apricot-updater/src/lib.rs` (70 lines total) defines only an `UpdateChannel` enum (`Stable`/`Beta`/`LocalOnly`, with the comment "Local Rust betas explicitly disable remote publication and installation" — this "LocalOnly" behavior is a code comment, not a user-approved deviation) and a `check_youtube_components` helper that iterates yt-dlp/rusty_ytdl component checks but is never called anywhere in the app (`grep -rn "check_youtube_components" crates/apricot-app crates/apricot-ui-windows apps/apricot-player` finds only its own definition and unit test). Settings screen exposes matching fields/buttons (`auto_update_ytdlp`, `app_update_interval_hours`, `check_app_updates_now`, `app_update_notifications`, `update_channel` in `crates/apricot-app/src/settings_model.rs:320-355,1188-1189`), consistent with the already-documented "settings command buttons stubbed" finding — they render but have no working action behind them.
- Python features with no working Rust equivalent (feature list, not line-level diffed):
  - Periodic/startup yt-dlp component update check and install: `apricot/updater/updater.py:41-185` (`start_ytdlp_update_check`, `update_ytdlp_worker`, `update_ytdlp_component_package`, `fetch_latest_ytdlp_wheel`, `reload_ytdlp_after_component_update`).
  - App self-update: version check, changelog prompt, download with SHA-256 verification, installer/portable-zip update script generation and self-relaunch: `updater.py:186-964` (`start_app_update_check`, `show_update_prompt`, `download_and_install_update`, `verify_release_asset_file`, `write_installer_update_script`, `write_portable_zip_update_script`, `exit_for_update`).
  - GitHub release/changelog fetching and version comparison used by both the manual "check for updates now" button and the periodic timer: `updater.py:964-1089` (`fetch_latest_release`, `fetch_github_latest_release`, `cumulative_changelog_text`, `is_newer_version`).
  - Skip-this-version behavior implied by `store_pending_app_update`/settings (`updater.py:249-267`) — no equivalent persisted "skip version" state found in Rust settings model.
- Net effect: an NVDA user on the Rust build who presses "Check for updates now" or expects periodic yt-dlp/app update checks (both of which exist as visible settings/menu entries) gets no feedback and no functionality, with no indication that the buttons are inert.

## 5. Needs runtime/NVDA verification

- PODDL-02: whether NVDA actually vocalizes the download-progress dialog's static-text percent updates while unfocused/focused, and at what practical frequency, for audio-only downloads that lack `--progress-delta` throttling in the Rust yt-dlp invocation.
- PODDL-01: whether Windows' own key-repeat rate for the configured download shortcut is fast enough in practice to trigger the duplicate-confirm-dialog/duplicate-task symptom described (this depends on the user's OS key-repeat delay/rate settings and how long a press is held).
- Whether the `type`/`podcast_episode` field difference in `rss_episode_label` (Rust always shows the current-language `podcast_episode` text regardless of any legacy/different-language value that might be persisted in older Python-authored `rss_feed_file` data) is user-visible in practice; likely low-impact since Python always stores the translated string at parse time too (`library.py:2121-2123`), so it would only surface after a live language change with pre-existing episodes, and was not confirmed as a live bug (kept out of the deviations table as P3/speculative).
