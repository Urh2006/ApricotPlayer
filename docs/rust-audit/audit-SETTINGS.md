# Settings dialog audit (Python vs Rust)

Status: IN PROGRESS - being written incrementally.

## 1. Summary

The Settings *data model* is very well ported: section order, per-section reset-field ownership, the customizable main-menu checklist, all 18 equalizer factory presets (exact gains), band/frequency ids, and the full `SettingsDocument` schema (field names, JSON keys, defaults, unknown-key preservation via `#[serde(flatten)]`) closely mirror Python's `Settings` dataclass, and Rust genuinely embeds all 27 of Python's own locale JSON files at compile time rather than a separate translation set.

However, the *interactive* Settings dialog is largely non-functional: `handle_settings_command()` in `settings_win32.rs` only implements the per-section "Reset" button — every other action (Browse folder, Set default player, Check for updates, Choose cookies file, Export/import browser cookies, Open YouTube login, Obtain API key, AudioVault login/logout/register, equalizer Add/Import/Export/Delete/Reset preset, Check subscriptions now) shows an un-localized "not implemented" MessageBox. The entire browser-cookie-extraction backend from `apricot/ui/cookies.py` (~950 lines, YouTube auth workflow) has no Rust equivalent at all. On top of that, the global "Reset all settings" button has the wrong label text and an extra un-localized confirmation dialog Python doesn't have, "Save" closes the whole window instead of staying open like Python's screen, and keyboard-shortcut conflict messages are un-localized and show raw action ids instead of translated labels.

Counts: **3 P1** (1 deviation SETTINGS-01 + 2 missing M-01/M-02), **5 P2** (SETTINGS-02/03/04/05 + missing M-03), **1 P3** (SETTINGS-06). 4 items flagged for runtime/NVDA verification.

## 2. Deviations in ported functionality

### SETTINGS-01 — P1 — Nearly all Settings command buttons are non-functional stubs
Python: settings.py wires every "action" button to a real handler: `browse` (choose_download_folder), `set_default_player` (open_windows_default_apps_settings), `check_ytdlp_updates_now` (manual_ytdlp_update_check), `check_app_updates_now` (manual_app_update_check), `choose_cookies_file`, `open_youtube_login_profile_from_settings`, `export_browser_cookies_from_settings`, `open_youtube_api_key_page_from_settings`, `login_audiovault_from_settings`/`logout_audiovault`/`open_audiovault_registration`, `subscription_check_now`, equalizer `add_equalizer_profile_from_settings`/`import_equalizer_profile_from_settings`/`export_visible_equalizer_profile_from_settings`/`delete_visible_equalizer_profile_from_settings`/`reset_visible_equalizer_controls` (apricot/ui/settings.py lines 398-414, 461-483, 593-681, 762-965).
Rust: `crates/apricot-ui-windows/src/settings_win32.rs` `handle_settings_command()` (lines 818-837) only implements `SettingsCommand::ResetSection`. Every other `SettingsCommand` variant (`BrowseDownloadFolder`, `BrowseCacheFolder`, `SetDefaultPlayer`, `CheckYoutubeComponentUpdates`, `CheckAppUpdates`, `CheckSubscriptions`, `ChooseCookiesFile`, `OpenYoutubeLoginProfile`, `ExportBrowserCookies`, `ObtainYoutubeApiKey`, `AudiovaultLogin`, `AudiovaultLogout`, `AudiovaultRegister`, `ResetEqualizerPreset`, `AddEqualizerProfile`, `ImportEqualizerProfile`, `ExportEqualizerProfile`, `DeleteEqualizerProfile`) falls into the `else` branch and just shows a MessageBox: `"{command:?} is not implemented in this internal build yet."`. Confirmed via repo-wide grep: these variant names appear only in `settings_model.rs` (construction) and this one match arm (stub) — no other file references them, and `apricot-app/src/settings_controller.rs` (245 lines) has no methods for folder browsing, cookie file selection, AudioVault auth, or equalizer preset CRUD.
Impact: pressing Browse, Set default player, Check for updates, Choose cookies file, Open YouTube login profile, Export browser cookies, Obtain YouTube API key, AudioVault login/logout/register, Reset equalizer preset, Add/Import/Export/Delete equalizer profile, and Check subscriptions now all do nothing but pop up an un-localized (hard-coded English) "not implemented" dialog. This is most of the interactive surface of the Settings dialog.
Suggested fix: implement each `SettingsCommand` against `Application`/`SettingsController`, reusing the folder-picker/dialog primitives already used elsewhere in the Win32 UI; until implemented, this should be treated as a known major gap, not treated as done in parity docs.

### SETTINGS-02 — P2 — Rust "Save" closes the settings window; Python "Save" stays open
Python: `save_settings_from_ui` (apricot/ui/settings.py:966-984) saves and shows a "settings_saved" status + speech, then keeps the Settings screen open (only re-renders if the language changed at apricot/ui/settings.py:983-984). The user can keep editing other sections after Save.
Rust: `save_and_close` (settings_win32.rs:862-893) always calls `DestroyWindow(window)` after saving, closing the whole Settings window immediately, with no "settings saved" confirmation text/speech equivalent.
Impact: NVDA users lose the "settings_saved" confirmation announcement and cannot keep editing after Save; the whole interaction model changes from "editable screen with Save/Back" to "modal OK/Cancel dialog".
Suggested fix: consider announcing a save confirmation (e.g. via accessible name change or a transient status) and confirm with the user whether closing-on-save is an intended architecture change; if so, document it as an approved deviation.

### SETTINGS-03 — P2 — Rust "Reset all settings" button uses wrong label text and adds an un-localized confirmation dialog not present in Python
Python: the global reset button in `show_settings()` (apricot/ui/misc.py:998) is labelled with locale key `restore_defaults` = "Restore to defaults" (apricot/locales/en.json:204) and `restore_default_settings()` (apricot/ui/settings.py:849-864) performs the reset immediately with NO confirmation dialog — it just resets, saves, and re-shows Settings with a spoken/status "defaults_restored" confirmation.
Rust: `ID_RESET_ALL` button is labelled via locale key `reset_all_settings` = "Reset all settings" (settings_win32.rs:307, settings_model.rs uses the same key text for the per-section reset button too, so the global button and the per-section button read almost identically). `reset_all()` (settings_win32.rs:902-921) shows a hard-coded, non-localized `MessageBoxW` ("Reset all ApricotPlayer settings to their defaults?" / title "ApricotPlayer 2 Beta") requiring Yes/No before proceeding — a confirmation step Python does not have, and its text will not translate for non-English NVDA users.
Impact: wrong/confusing button label parity (P3-ish on its own) plus an extra un-localized modal dialog Python users never see (P2) — for a screen-reader user relying on translated UI this dialog reads as an untranslated English string in every non-English locale.
Suggested fix: use `restore_defaults` catalog key for the button label to match Python text, and either remove the confirmation (matching Python) or localize it via the catalog if the confirmation is an intentional (but unapproved) safety improvement.

### SETTINGS-04 — P2 — Rust "general" section has an extra "YouTube backend" control not present in Python
Python: `settings_section_fields()["general"]` (apricot/ui/settings.py:118-133) and the "general" rendering block (apricot/ui/settings.py:451-486) have no youtube-backend selector; Python's `Settings` model has no such field either (grep of apricot/models.py shows no `youtube_backend`).
Rust: `general_controls()` (settings_model.rs:303-316) inserts a `SettingsControl::Choice` for `SettingId::YoutubeBackend` ("yt-dlp" vs "rusty_ytdl") between `ShowShortcutsInLabels` and `AutoUpdateYtdlp`, confirmed by the unit test `general_controls_preserve_python_order_and_current_values` expecting `model.controls.len() == 19` (Python's general section renders 18 total widgets including the per-section reset button, counted from settings.py: language, settings_file, download_folder, browse, set_default_player, results_limit, direct_link_enter_action, show_shortcuts_in_labels, auto_update, auto_update_app, update_channel, app_update_interval, check_ytdlp_updates_now, check_app_updates_now, close_to_tray, start_with_windows, tray_notification = 17 + reset = 18).
Impact: an extra Tab stop/combo box with no Python equivalent shifts the tab order of every subsequent control in the General section and exposes a setting NVDA users of the Python version never see. This may be a deliberate consequence of the Rust build having two YouTube backends, but it is a Rust-only UI addition and not an approved deviation per the audit brief.
Suggested fix: confirm with the user whether this control is intentional; if so, document as an approved deviation, otherwise remove it from the General section model or gate it behind a build flag that keeps parity builds free of it.


### SETTINGS-05 — P2 — Keyboard-shortcut conflict message is un-localized and names the raw internal action id, not a human label
Python: `on_shortcut_capture_key` (apricot/ui/shortcuts.py:203-233) detects a conflict via `shortcut_conflict()` and shows `wx.MessageBox(self.t("shortcut_in_use", shortcut=shortcut, action=self.t(conflict[1])), self.t("shortcut_in_use_title"), wx.OK | wx.ICON_WARNING)` plus `self.speak_text(message)` — fully localized, using the conflicting action's translated label (e.g. "Play/Pause"), and leaves the text control unfocused/unchanged so the user can retry.
Rust: `capture_shortcut` (settings_win32.rs:1097-1131) calls `app.set_keyboard_shortcut`; on conflict it shows the raw Rust error via `show_error` (settings_win32.rs:1614-1622), whose text comes from `SettingsControllerError::ShortcutConflict` (`settings_controller.rs:21-22`): `"shortcut {shortcut} is already assigned to {action}"` where `{action}` is literally the internal action id string (e.g. `player_play_pause`), not a translated label — and the whole sentence is hard-coded English, never localized, with a generic `MB_ICONERROR` and title "ApricotPlayer 2 Beta" instead of Python's warning icon and "shortcut_in_use_title" text.
Impact: non-English NVDA users hear an English sentence with a raw snake_case identifier instead of a friendly translated action name; the icon/severity semantics also differ (Error vs Warning).
Suggested fix: route the conflict result through the translation catalog (`shortcut_in_use`/`shortcut_in_use_title` keys) and resolve the conflicting action id to its catalog label before displaying.

### SETTINGS-06 — P3 (needs runtime verification) — Settings-section switching has no debounce in Rust, unlike Python's 140 ms coalescing delay
Python: arrow-key navigation within the section `wx.ListBox` triggers `on_settings_section_changed`/`_sync_settings_section_from_list`, which only marks the target section "pending" and schedules the actual re-render via `wx.CallLater(140, ...)` (apricot/ui/settings.py:248-311); rapid Up/Down browsing therefore does not rebuild the whole control panel on every keystroke, only after the user pauses (or explicitly commits with Tab/Enter, which flushes immediately and also moves focus into the first control).
Rust: `change_section()` (settings_win32.rs:839-860) runs synchronously on every `LBN_SELCHANGE` (i.e. every arrow keypress in the list), destroying and recreating every dynamic control in the pane immediately, then re-focuses the section list (matching Python's "stay on the list while browsing" behavior for focus, but not the debounce).
Impact: holding Up/Down to skim through the 11 sections rebuilds the whole Win32 control tree on each step instead of once after the user stops, which may be perceptible as lag/flicker to a keyboard user, though functionally the end state is the same once navigation stops.
Suggested fix: consider coalescing rapid selection changes (e.g. a short timer) to match Python's behavior; verify at runtime whether this is actually noticeable before prioritizing.

## 3. Missing functionality

### SETTINGS-M-01 — P1 — Entire browser-cookie import/export backend is missing in Rust
Python: `apricot/ui/cookies.py` (956 lines, `CookiesUI` mixin) implements: discovering legacy cookie sources, locating cookies files, matching/validating cookie sources, decoding cookie file bytes/JSON/Netscape/header formats, building `http.cookiejar` jars, importing a cookie file into the app cache, discovering per-browser cookie profiles (Chrome/Edge/Firefox/Brave/Chromium/Opera/Vivaldi), locating each browser's executable, exporting cookies from a running Chromium browser via a DevTools websocket (`export_chromium_cookies_via_devtools`), scoring/validating exported cookie jars for YouTube login cookies, and repairing cookie-related auth errors. All of it is reachable from the Settings > Cookies section (`choose_cookies_file`, `export_browser_cookies_from_settings`, `open_youtube_login_profile_from_settings` in apricot/ui/settings.py:656-676, 901-956).
Rust: repo-wide grep for cookie-related logic (`discover_cookie_profiles`, `export_chromium_cookies_via_devtools`, `cookie_jar_from_json_data`, etc.) finds nothing outside `settings_model.rs`'s UI labels/options and `settings.rs`'s plain `cookies_file`/`cookies_from_browser`/`cookies_browser_profile` string fields — there is no cookie-jar parsing, browser discovery, or DevTools export code anywhere in `crates/` or `apps/`. The corresponding Settings buttons are the stubs described in SETTINGS-01.
Impact: NVDA users cannot use any of the multiple ways Python offers to authenticate cookies for age-restricted/region-locked YouTube content (manual file, browser auto-import, DevTools export) — a core workflow for reliable playback.
Suggested fix: port `apricot/ui/cookies.py`'s logic into a new `apricot-network`/`apricot-platform` module and wire it to the existing `SettingsCommand::ChooseCookiesFile` / `ExportBrowserCookies` / `OpenYoutubeLoginProfile` stubs.

### SETTINGS-M-02 — P1 — Equalizer preset management (add/import/export/delete/reset) has no working backend
Python: `apricot/ui/settings.py` 762-846 and `apricot/ui/equalizer.py` implement creating a new custom preset from current sliders (`create_equalizer_profile_dialog`), importing/exporting a preset to/from a file, deleting a custom preset with automatic fallback selection, and resetting the visible sliders to the preset's saved values.
Rust: `SettingsCommand::ResetEqualizerPreset`, `AddEqualizerProfile`, `ImportEqualizerProfile`, `ExportEqualizerProfile`, `DeleteEqualizerProfile` are all unhandled stubs (see SETTINGS-01); `SettingsController`/`Application` expose no corresponding methods (grep found none).
Impact: users can toggle the equalizer, pick an existing factory preset, and drag the band sliders, but cannot create, name, import, export, or delete their own presets — a core part of the equalizer workflow is unusable.
Suggested fix: same as SETTINGS-M-01 — implement the missing controller methods and wire them to the existing command stubs.

### SETTINGS-M-03 — P2 — "Set default player" (Windows default-apps association) has no Rust implementation
Python: `open_windows_default_apps_settings` (bound at apricot/ui/settings.py:462) opens the Windows "Default apps" settings page for a media-association workflow.
Rust: `SettingsCommand::SetDefaultPlayer` is an unhandled stub (SETTINGS-01); no code elsewhere in the Rust tree opens `ms-settings:defaultapps` or similar.
Impact: users cannot register ApricotPlayer as a default handler for supported files from within Settings.
Suggested fix: implement via `ShellExecuteW` on `ms-settings:defaultapps` (or the appropriate per-app protocol), matching Python's target.



## 4. Verified as matching

- Section list and order: Python's 11 sections (`settings_sections()`, apricot/ui/settings.py:92-105) match Rust's `SettingsSection::ALL`/`SETTINGS_SECTIONS` (apricot-core/src/settings_layout.rs:21-33, 201-257) exactly in order and label keys (general, main_menu, playback, equalizer, downloads, library, podcasts, notifications, cookies, audiovault, shortcuts).
- Per-section "reset section" field ownership: Rust's `reset_fields` lists in settings_layout.rs match Python's `settings_section_fields()` (apricot/ui/settings.py:115-245) field-for-field and in the same order for every section except `general`, which has the extra `YoutubeBackend` field (SETTINGS-04); `app_update_notifications` is correctly owned by both `general` and `notifications` on both sides.
- Customizable main-menu checklist: Rust's `CUSTOMIZABLE_MAIN_MENU` (apricot-core/src/menu.rs) matches Python's `MAIN_MENU_CUSTOMIZABLE_ITEMS` (apricot/constants.py:612-632) exactly — same 19 action ids, same order, same label keys (including the special "Search YouTube / SoundCloud" combined label for "search"), and `settings`/`exit` are correctly excluded from customization on both sides.
- Equalizer data: Rust's `FACTORY_EQUALIZER_PRESETS` (apricot-core/src/audio.rs) matches Python's `EQ_FACTORY_PRESET_VALUES` (apricot/constants.py:403-422) exactly for all 18 presets — same ids and per-band dB gains — and `CUSTOM_EQUALIZER_PRESET_IDS`/`EQ_CUSTOM_PRESET_IDS` both list `custom1`/`custom2`/`custom3`. `EQUALIZER_BANDS` (10 bands, 31 Hz–16 kHz) matches Python's `EQ_BANDS` ids/frequencies exactly, and both support the same `EQ_RANGE_OPTIONS`/`["6","12","18","24"]` dB range choices and a clipping-protection toggle.
- Settings storage schema: `SettingsDocument` (apricot-storage/src/settings.rs) mirrors nearly every field of Python's `Settings` dataclass (apricot/models.py) with matching JSON key names and matching default values (spot-checked: `replaygain_mode="no"`, `pitch_mode`/`speed_audio_mode` default strings, `direct_link_enter_action="play"`, `cookies_browser_profile="auto"`, `video_format="mp4"`, etc.), plus a `#[serde(flatten)] preserved: BTreeMap<String, Value>` catch-all that round-trips unknown keys, and `from_value_with_defaults` merges a real Python `settings.json` over Rust defaults before validating — so Rust can read an authentic Python settings file without data loss.
- Locale catalog: `embedded_catalog()`/`locale_source()` (apricot-app/src/main_menu.rs:134-193) embed all 27 language JSON files directly from the Python source tree (`include_str!("../../../apricot/locales/<code>.json")`) at compile time, for the exact same 27 `LANGUAGES` codes declared in apricot-core/src/locale.rs — i.e. Rust reuses Python's own translated strings rather than a separate/duplicated set, so wording parity for translated text is inherently high wherever the catalog is actually used.
- Per-section control counts and field order for Playback (34), Downloads (22), Library (6), Podcasts (8), Notifications (4), Cookies (12 base + 4 conditional advanced fields), Audiovault (2), Shortcuts (1) sections match Python 1:1, including the conditional reveal of advanced network settings only when `show_advanced_network_settings` is on (both sides).
- Shortcut capture UX basics: Tab is passed through (not captured) on both sides; Space is ignored as a shortcut trigger except for `player_play_pause` on both sides; captured shortcuts are rendered as `Ctrl+Shift+Alt+Key` in the same canonical order on both sides.



## 5. Needs runtime/NVDA verification

- SETTINGS-06 (section-switch debounce removed): whether rebuilding the whole control pane on every arrow-key press while browsing sections is actually perceptible as lag or extra NVDA chatter versus Python's 140 ms-coalesced re-render — could not be confirmed without running the built app under NVDA.
- Actual MSAA/UIA accessible names and roles for each Win32 control type (COMBOBOX, EDIT, BUTTON, trackbar, LISTBOX) as announced by NVDA were not verified against wx's accessible name/role for the equivalent control — the code paths (`SetWindowTextW` for trackbar accessible names, `SetWindowSubclass`-based focus routing) look correct on paper but were not exercised live.
- Whether `IsDialogMessageW`'s built-in Tab handling for the Settings window matches Python's `apply_settings_tab_order()`/`MoveAfterInTabOrder` ordering exactly for every dynamically inserted control, especially after `render_controls()` recreates the whole control set (e.g. does Tab order still visually/logically follow top-to-bottom reading order after several section switches) — plausible from the code but not confirmed interactively.
- Whether the un-localized "not implemented in this internal build yet." MessageBox (SETTINGS-01) is read correctly and non-disruptively by NVDA (e.g. does it steal focus predictably, is it dismissed cleanly with Escape/Enter) — likely fine since it's a standard `MessageBoxW`, but not confirmed live.
- Whether `default_volume`'s max value (100 vs 300 when `volume_boost_by_default` is toggled) live-updates the slider's range and announced value the moment the checkbox is toggled in Rust, matching Python's `on_volume_boost_by_default_settings_changed` immediate slider adjustment (settings.py:550-551) — Rust's `dependent_setting()` does list `VolumeBoostByDefault` as triggering a re-render (settings_win32.rs:788), which looks correct, but the resulting focus/announcement was not observed live.
