# LIBRARY audit (in progress)

Area: local media and library collections, plus user-data compatibility.

## Deviations (draft, appended incrementally)

### LIBRARY-01 (P2) — Play-folder list is batched to 20 items in Rust, loaded in full in Python
- Python: `apricot/ui/misc.py:1252-1317` `show_local_media_folder()` calls `self.show_results(folder_items, selection=selection, visible_count=len(folder_items))` — the ENTIRE folder listing is put into the ListBox immediately (no incremental batches; `self.dynamic_fetch_enabled = False` at line 1304).
- Rust: `crates/apricot-app/src/local_folder.rs:8` `DEFAULT_FOLDER_BATCH_SIZE = 20`; `LocalFolderSession::load()` sets `visible_count = batch_size.min(items.len())`, and `crates/apricot-ui-windows/src/win32.rs:9757` `local_folder_selection_changed()` / `append_local_folder_batch()` only reveal 20 more rows at a time as the user reaches the end of the visible batch.
- Effect: for a folder with more than 20 files, Python's NVDA user hears/sees every file in the list right away (Ctrl+End jumps to the true last track). In Rust only the first 20 rows exist until the user arrows/End's past the last visible row to trigger another batch — jumping straight to the end (e.g. via search-as-you-type or an assumption that all items are loaded) will not reach the real last file until batches are exhausted.
- Suggested fix: either load the whole folder into the list at once (matching Python), or explicitly confirm with the user this batching is an approved deviation.

### LIBRARY-02 (P2) — Favorites/History context menus don't branch on local-file vs remote item, and are missing several items
- Python: `apricot/library/library.py:443-481` `open_favorites_context_menu()` — two completely different menus depending on `item_is_local_media(selected)`:
  - Local-file favorite: play, add_to_playlist, add_to_playback_queue, remove_from_playback_queue, **copy_path**, remove.
  - Remote favorite: play, download_audio, download_video, subscribe_channel, unsubscribe_channel, [open_channel if `item_has_openable_youtube_channel`], add_to_playlist, add_to_playback_queue, **remove_from_playback_queue**, **copy_stream_url**, copy_url, remove.
  Same local/remote split exists for history: `apricot/library/library.py:578-614` `open_history_context_menu()` (adds `add_favorite` and always has `remove_history_item`/`clear_history`).
- Rust: `crates/apricot-ui-windows/src/win32.rs:2041-2064` `list_context_entries()` builds one fixed menu for `MainView::Favorites` and one fixed menu for `MainView::History`, regardless of whether the selected item is local media:
  - Favorites: play, download_audio, download_video, add_to_playback_queue, copy_link, remove_favorite, subscribe_channel, unsubscribe_channel, add_to_playlist.
  - History: play, download_audio, download_video, add_favorite, add_to_playback_queue, copy_link, remove_history_item, clear_history, subscribe_channel, unsubscribe_channel, add_to_playlist.
- Concrete deviations:
  1. A local-file favorite/history entry in Rust still offers "download_audio"/"download_video"/"subscribe_channel"/"unsubscribe_channel" — actions that make no sense on a local file and that Python never shows for local media.
  2. `remove_from_playback_queue` is entirely absent from both Rust menus (present in every Python variant).
  3. `copy_stream_url` ("Copy direct media URL") is entirely absent from the Rust remote-item menu.
  4. The conditional `open_channel` entry (shown by Python when `item_has_openable_youtube_channel(selected)`) is not in the Rust list at all for Favorites/History.
  5. Rust's single "copy_link" ("Copy link") label is used everywhere, where Python uses "copy_url" ("Copy URL") for remote items and "copy_path" ("Copy path") for local-file items — different locale keys/text an NVDA user would hear.
- Suggested fix: branch `list_context_entries` for `MainView::Favorites`/`MainView::History` on the selected item's local-vs-remote kind (mirroring `item_is_local_media`), add the missing `remove_from_playback_queue`, `copy_stream_url`, and conditional `open_channel` entries, and use `copy_path`/`copy_url` per item kind instead of a single `copy_link`.

### LIBRARY-03 (P3) — User-playlists list context menu has extra items/order not present in Python, no rename (matches Python — not missing)
- Python: `apricot/ui/menus.py:255-269` `open_user_playlists_context_menu()` — exactly 4 items, in this order: `open_playlist`, `create_playlist`, `download_user_playlist`, `remove_playlist`. No rename, no play/shuffle-playlist-from-list, no add-to-queue.
- Rust: `crates/apricot-ui-windows/src/win32.rs:2112-2120` `MainView::UserPlaylists` context menu: `open_playlist`, `create_playlist`, `play_playlist`, `shuffle_playlist`, `add_to_playback_queue`, `download_user_playlist`, `remove_playlist` — three extra entries not present in Python's source-of-truth menu, changing both the item set and the position of `download_user_playlist`/`remove_playlist` relative to Python.
- Impact: NVDA users familiar with Python will hear extra menu items in a different order; functionally harmless (adds capability) but is a concrete deviation from the source of truth and should be confirmed as an approved addition.

## Missing functionality

### LIBRARY-M-01 (P1) — Opening a favorited/history'd channel or playlist item does nothing but show an error; Python navigates into it
- Python: `apricot/ui/lists.py:809-824` `open_library_item(item, screen)` — when `item.get("kind")` is `"channel"` or `"playlist"`, it pushes the current screen onto `search_results_stack`, switches into the search/results view, and calls `open_channel_videos`/`open_soundcloud_artist_tracks`/`open_playlist_videos` to navigate into that collection's contents. This is reached from `play_favorite()` (`apricot/ui/misc.py:3329-3332`, always calls `open_library_item(item, "favorites")`) and equivalently from history (`play_history_item`, which follows the same `open_library_item` path per `apricot/library/library.py` history wiring).
- Rust: `crates/apricot-ui-windows/src/win32.rs:3371-3399` `activate_collection_selection()` — for `MainView::Favorites`/`MainView::History`, if `item.kind` is `Playlist` or `Channel` it calls `show_error_message` with literally: *"{title} is preserved in favorites, but collection navigation is not implemented in this internal build yet."* and returns, instead of opening the channel/playlist contents. This applies both to pressing Enter (`activate_collection_selection`) and (per the file's own admission) generally — there is no code path in this file that opens a favorited/history'd channel or playlist.
- Effect for NVDA users: a favorited YouTube channel or playlist can be added to Favorites/History (and shown in the list with correct text), but activating it is a dead end — the user gets an English-only error dialog instead of the channel/playlist's video list. This is a real, user-visible capability loss versus Python, not a cosmetic gap.
- Suggested fix: wire `activate_collection_selection` (and the double-click / Enter handlers for Favorites and History) to open channel/playlist contents the same way search-result activation does (reuse whatever `open_youtube_collection`/`YoutubeCollectionKind` machinery already exists for `MainView::Results`), matching `open_library_item`'s branch in Python.

## Verified as matching (brief)
- Local-media extension set (`LOCAL_MEDIA_EXTENSIONS` after `CONVERTER_MEDIA_EXTENSIONS` merge, `apricot/constants.py:424-483`) matches Rust's `MEDIA_EXTENSIONS` in `crates/apricot-platform/src/local_media.rs:14-20` (53 extensions, including `alac`/`asf` picked up from the converter-extension merge).
- Natural sort algorithm (`natural_sort_key` in `apricot/ui/misc.py:1223-1228`, filename-extension-aware, digit-run comparison) is faithfully reimplemented in `crates/apricot-platform/src/local_media.rs:189-263` (`natural_parts`/`natural_cmp`), including the extension-isolation trick (`\x00` splitting the extension) and locale-independent numeric comparison for arbitrarily large digit runs. Recursive, non-symlink-following folder scan matches Python's `os.walk`-based `local_media_files_in_folder` (`apricot/ui/system.py:411-429`).
- Bookmarks feature (`apricot/ui/misc.py:1378-1709`) is faithfully ported in `crates/apricot-ui-windows/src/bookmark_dialog_win32.rs` + `crates/apricot-app/src/bookmark_controller.rs` + wiring in `win32.rs` around line 11303-11620: same list/Add/Play/Rename/Delete/Copy-timestamp actions, Delete key deletes immediately with no confirmation (matches Python), sorting (`sorted()`/`for_item()`) mirrors Python's `sorted_bookmarks()`/`bookmarks_for_item()` (case-insensitive title, then position, then name), and the `copy_timestamp_link` action correctly gates on YouTube-only availability (`youtube_url_at_timestamp`) in both.
- "Resume last session" main-menu visibility gating exactly matches Python: `settings.show_resume_in_menu && last session available` (`apricot/ui/menus.py:59` vs `crates/apricot-app/src/application.rs:1943`).
- Cross-version data-compatibility import mechanism (asked for explicitly by the task): Rust beta (`%APPDATA%\ApricotPlayer2Beta`) is a fully separate profile from Python's stable `%APPDATA%\ApricotPlayer` (`crates/apricot-platform/src/paths.rs`, `ApplicationIdentity::RustBeta` sets `legacy_app_data` = the stable Python directory). On every launch, each collection controller (`BookmarkController`, and by the same pattern favorites/history/subscriptions/rss/playlists/playback-positions/last-session/playback-queue, wired in `apps/apricot-player/src/main.rs:62-102`) is constructed with `(current_beta_file, &legacy_python_file)`: if the beta file already exists it is used exclusively; only if the beta file is absent does it read the Python stable file, and it then immediately writes that imported data into the beta file (confirmed for bookmarks in `crates/apricot-app/src/bookmark_controller.rs:27-58`, and by dedicated tests `stable_bookmarks_are_imported_without_modifying_stable_data` / `stable_queue_is_migrated_without_writing_back_to_stable`). So: the user's real Python data CAN be read and is imported automatically and losslessly on Rust's first run, it is a one-time copy (not a live sync — later Python-side edits are not picked up once the beta file exists), and the stable Python files are never modified. This matches the expected/sane behavior; no deviation found here.
- `MediaItem` <-> Python-dict conversion (`crates/apricot-storage/src/legacy_media.rs`) round-trips unknown/future JSON fields via a catch-all `metadata` map on both `MediaItem` and playlist/bookmark structs (`user_playlist_file.rs`, `bookmark_file.rs`), so fields Python writes that Rust doesn't model explicitly are preserved on save rather than dropped — good data-fidelity design, at least for the sampled files (favorites/history/playlists/bookmarks share this pattern).

## Needs runtime/NVDA verification
- LIBRARY-01 (folder batching): whether the 20-item initial batch is confirmed at runtime to actually block reaching later files via Ctrl+End / accessible "jump to last item" gestures, versus being effectively invisible because arrowing down always triggers `append_visible_batch()` before the user notices. Static code review shows the batch exists; actual NVDA-perceived impact should be confirmed by loading a >20-file folder.
- LIBRARY-M-01: confirm in a running build that favoriting an actual YouTube channel/playlist (not just a video) is reachable at all from search results (to know how common this scenario is for users), and that the error dialog text is not localized (it appears to be a hard-coded English `format!` string with no catalog key, which — if confirmed — is an additional, separate localization gap worth its own follow-up).
- Whether Rust's added "play_playlist"/"shuffle_playlist"/"add_to_playback_queue" entries in the user-playlists list context menu (LIBRARY-03) are an intentionally-approved Rust enhancement or an unreviewed scope creep; only the user/maintainer can say which.
