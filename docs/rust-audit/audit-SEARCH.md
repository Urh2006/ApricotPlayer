# Audit: Search & Online Sources (KEY=SEARCH)

Compared Python `origin/main fe62a21` (`apricot/search/search.py`, `apricot/ui/lists.py`, `apricot/ui/misc.py`, `apricot/ui/menus.py`, `apricot/ui/system.py`, `apricot/network/youtube.py`, `apricot/player/playback.py`) against the Rust port (`crates/apricot-ui-windows/src/win32.rs`, `crates/apricot-app/src/{search_session,youtube_collection,youtube_trending}.rs`, `crates/apricot-platform/src/ytdlp_youtube.rs`, `crates/apricot-core/src/context_menu.rs`).

## 1. Summary

The dynamic-loading pagination engine (`SearchSession` in `search_session.rs`) is a careful, well-tested 1:1 port of Python's 20-item incremental growth, generation-scoped stale-response rejection, and selection-preserving merge logic. Trending country/category persistence, focus order, and the "channel options" tab order (videos/playlists/streams/popular) and their URL mapping also match Python closely. However, **the entire SoundCloud search provider is missing from the Rust search screen** — there is no provider selector, no Track/Playlist/User search types, and no SoundCloud search/entry-extraction code path anywhere in the Rust workspace outside of a dead `MediaSource::Soundcloud` enum variant. This is the largest finding in this area (P1). The results-list context menu also drops the "Open in browser" action present in every branch of Python's `open_context_menu`, mislabels "Copy URL" as "Copy link", omits playlist item counts from playlist rows, and adds a "channel download" submenu Python does not offer for channels. The already-known missing `open_channel`/`result_column_previous`/`result_column_next` shortcut handlers in `activate_action()` (see `audit-SHELL.md`) also affect this area's context-menu parity (no `open_channel` menu entry either).

Counts: deviations **1 P1, 4 P2, 4 P3** (9 total); missing functionality **2 P1, 2 P2** (4 total). Combined: **3 P1, 6 P2, 4 P3** across 13 findings.

## 2. Deviations in ported functionality

### SEARCH-01 — P1 — SoundCloud search provider entirely absent from the search screen UI
- Python: `apricot/search/search.py:111-127` (`self.search_provider = wx.Choice(..., choices=[self.t("youtube"), self.t("soundcloud")])`, `on_search_provider_change`, `search_type_definitions()` returning `Track/Playlist/User` for provider index 1).
- Rust: `crates/apricot-ui-windows/src/win32.rs` — `WindowState` has no `search_provider`/provider `HWND` field at all (only `search_label`, `search_edit`, `kind_label`, `kind`, `search`, `back`; see struct at line ~394-402). The type combobox is hard-coded to 4 YouTube-only entries: `for key in ["all", "video", "playlist", "channel"]` (line 1048) and `selected_search_kind()` (line 10406-10414) maps only to `YoutubeSearchKind::{All,Video,Playlist,Channel}`. No SoundCloud choice exists anywhere in the search screen.
- Description: An NVDA user has no way to search SoundCloud at all from the main Search screen; the "provider" concept from Python (which drives type choices, URL building, and the whole `soundcloud_search_entries`/`normalize_entry` SoundCloud branch) simply does not exist in Rust's search flow.
- Suggested fix: Add a provider `wx.Choice`-equivalent combobox to the search screen, wire `on_search_provider_change` equivalent to repopulate the type combobox with Track/Playlist/User when SoundCloud is selected, and implement SoundCloud search extraction (see SEARCH-M-01).

### SEARCH-02 — P2 — Results context menu is missing "Open in browser" for every kind (video/playlist/channel)
- Python: `apricot/ui/menus.py:391,404,415,443` — every branch of `open_context_menu` (SoundCloud channel, YouTube channel, playlist, plain video/track) includes `(self.t("open_browser"), self.open_selected_in_browser)`.
- Rust: `crates/apricot-ui-windows/src/win32.rs:1988-2028` (`list_context_entries` for `MainView::Results | Trending | YoutubeCollection`) — none of the Playlist/Channel/default(video) branches include `ID_CONTEXT_OPEN_BROWSER`. Confirmed by grep: `ID_CONTEXT_OPEN_BROWSER` is only used for `MainView::RssItems` (line 2103) and `MainView::PodcastSearchResults` (line 2108); the `open_browser` button (`state.open_browser`, line 1345) is likewise only shown for the podcast-search screen (line 2803).
- Description: NVDA users searching YouTube/SoundCloud, browsing trending, or a channel's videos/playlists cannot open the selected item on the website via the context menu, unlike Python.
- Suggested fix: Add `(ID_CONTEXT_OPEN_BROWSER, "open_browser")` to the video/playlist/channel entries returned by `list_context_entries` for the Results/Trending/YoutubeCollection views, and implement `open_selected_in_browser` equivalent (`ShellExecute` on the item URL).

### SEARCH-03 — P3 — "Copy URL" context-menu item is mislabeled "Copy link"
- Python: `apricot/ui/menus.py:392,405,416,445` — `self.menu_label_with_shortcut("copy_url", "copy_link")`; the first argument is the **label** locale key. `apricot/locales/en.json:266` → `"copy_url": "Copy URL"`.
- Rust: `crates/apricot-ui-windows/src/win32.rs:1996,2009,2021` — `(ID_CONTEXT_COPY_LOCATION, "copy_link")`, and `apply_list_context_entries`'s only override for this id is for local media (`"copy_path"`, line 1802-1804). The catalog key `"copy_link"` resolves to `"Copy link"` (`en.json:196`), not `"Copy URL"`.
- Description: Screen-reader announced label text differs from Python for this very common context-menu item on every search/trending/channel/playlist row.
- Suggested fix: Use `"copy_url"` as the catalog key for `ID_CONTEXT_COPY_LOCATION` in the Results/Trending/YoutubeCollection non-local branch (keep `"copy_path"` for local media, as already done).

### SEARCH-04 — P3 — Playlist result rows never show the item count
- Python: `apricot/ui/lists.py:629-634` — playlist rows append `self.playlist_count_text(item)` (`"{count} videos"`, `apricot/player/playback.py:172-180`) when `playlist_count`/`n_entries`/`video_count` is present in the entry.
- Rust: `crates/apricot-ui-windows/src/win32.rs:10356-10371` (`result_label`) — for `MediaKind::Playlist | MediaKind::Channel` it always returns `format!("{} | {kind}", item.title)` with no count segment, regardless of available metadata.
- Description: When yt-dlp/flat extraction does return a playlist video count, Python's row announces it (e.g. "My Mix | Playlist | 42 videos"); Rust's row never does.
- Suggested fix: In `result_label`, for `MediaKind::Playlist`, append a formatted count segment when `item.metadata` has a usable count field, mirroring `playlist_count_text`.

### SEARCH-05 — P2 — Channel context-menu row order and content differ from Python (extra download submenu, no `open_channel`)
- Python: `apricot/ui/menus.py:394-406,418-420` — non-SoundCloud channel menu is: `channel_options, channel_videos, channel_popular, channel_playlists, channel_live_streams, [sep], subscribe_channel, unsubscribe_channel, add_favorite/remove_favorite, open_browser, copy_url`. There is **no download entry** for channel rows in Python (only playlists get the `(None, None)` sentinel that triggers `append_collection_download_submenu`).
- Rust: `crates/apricot-ui-windows/src/win32.rs:1998-2011` — Channel entries are `channel_options, channel_videos, channel_popular, channel_playlists, channel_live_streams, download_audio, download_video, [subscribe/unsubscribe], favorite, copy_link`, and `collection_download_submenu_key` (line 1816-1822) turns the `download_audio`/`download_video` pair into a "download_channel" submenu (`append_collection_download_submenu`, line 1824-1845) for `MediaKind::Channel`.
- Description: Rust adds a whole-channel-download submenu that Python's context menu does not offer at all for channel rows (channels are only downloadable in Python via the collection screen after opening a tab), and the ordering (download items before subscribe/favorite) differs from Python's (subscribe/favorite before open_browser/copy). `channel_popular` and `channel_playlists` order also differs (Python: popular before playlists; Rust: playlists before popular... actually verify — Rust: channel_videos, channel_popular, channel_playlists, channel_live_streams matches Python's order videos→popular→playlists→streams). The `open_browser` item is also missing here (see SEARCH-02).
- Suggested fix: Remove the download submenu from the channel context-menu branch (or confirm with the user whether this is an intentional, approved enhancement) and match Python's item order/content otherwise.

### SEARCH-06 — P2 — Video-row context menu omits `remove_from_playlist` and `open_channel`, and reorders subscribe/download vs. Python
- Python: `apricot/ui/menus.py:432-448` — order for a plain video/track: `play, download_audio, download_video, add_favorite/remove_favorite, subscribe_channel/unsubscribe_channel, add_to_playback_queue, remove_from_playback_queue, remove_from_playlist, open_browser, copy_stream_url, copy_url`, plus conditional `open_channel` inserted at index 7 when `item_has_openable_youtube_channel(item)`, plus an "Add to playlist" submenu appended after the loop (`append_add_to_playlist_menu`).
- Rust: `crates/apricot-ui-windows/src/win32.rs:2012-2025` — order is `play, favorite, [subscribe/unsubscribe], download_audio, download_video, add_to_playback_queue, remove_from_playback_queue, playback_queue(open), copy_link, copy_stream_url, add_to_playlist`. There is no `remove_from_playlist` entry and no `open_channel` entry anywhere in this menu (consistent with the already-known missing `activate_action()` handler for `open_channel`, see `audit-SHELL.md`); `playback_queue` (open the playback-queue screen) is an addition not present in Python's results context menu.
- Description: An NVDA user cannot remove a search-result video from a user playlist via the context menu (no equivalent action reachable from results), and cannot jump to the item's channel from the menu (only via the separately-missing `open_channel` shortcut).
- Suggested fix: Add `remove_from_playlist` and a conditional `open_channel` entry (mirroring `item_has_openable_youtube_channel`) to the video-row entries in `list_context_entries`.

### SEARCH-07 — P3 — SoundCloud-channel-specific simplified context menu does not exist (falls out of SEARCH-01)
- Python: `apricot/ui/menus.py:385-393` — SoundCloud channel rows get a distinct, shorter menu (`open` [= open artist tracks], favorite, `open_browser`, `copy_url`) with no subscribe/unsubscribe (SoundCloud channels aren't subscribable).
- Rust: N/A — unreachable because SoundCloud items never appear in results (SEARCH-01).
- Description: Recorded for completeness; resolved automatically once SEARCH-M-01 is implemented, but the differentiated-menu logic itself will also need porting at that time.

### SEARCH-08 — P2 — Search screen has no dedicated Play / Download Audio / Download Video / Add Favorite buttons
- Python: `apricot/search/search.py:130-138` — `add_button_row([(search), (play), (download_audio), (download_video), (add_favorite)])`, all Tab-reachable, native buttons with accessible names, in addition to the shortcuts and context menu.
- Rust: `crates/apricot-ui-windows/src/win32.rs` `WindowState` — only `search` and `back` buttons exist for the Search view (grep for `play: HWND`, `download_audio: HWND`, `add_favorite: HWND` on the search screen returns nothing; these actions are reachable only via keyboard shortcuts and the context menu).
- Description: A keyboard user who tabs through the Search screen in Rust cannot discover or activate Play/Download Audio/Download Video/Add Favorite as buttons the way Python exposes them; they must already know the shortcuts or open the context menu. This changes the Tab order and the set of accessible controls on the screen.
- Suggested fix: Confirm with the user whether this is an accepted simplification (shortcuts+context menu cover the same actions) or should be ported as visible buttons for discoverability parity.

### SEARCH-09 — P3 — "Rusty YTDL" backend is a Rust-only deviation with a real UI/behavioural footprint
- Python: no equivalent setting; all YouTube extraction goes through yt-dlp.
- Rust: `crates/apricot-storage/src/settings.rs:142,267,385` (`youtube_backend` setting, default `"yt-dlp"`), exposed in Settings UI (`crates/apricot-app/src/settings_model.rs:291-312`), and consulted at multiple call sites in `win32.rs` (search/backend selection at lines 3318, 3580, 6195, 8411, 8557, 9481) and `collection_backend()` (line 8625-8627, which forces `YoutubeBackend::YtDlp` for every collection kind except `PlaylistVideos` when Rusty YTDL is selected).
- Description: This is the explicitly-flagged deviation from the audit brief — record it as approved-but-must-be-documented. It changes search/resolve code paths and behaviour (e.g. different failure modes/latency) depending on a setting Python users never see, and partially falls back to yt-dlp per-kind, which is behaviour with no Python analogue at all.
- Suggested fix: No fix required per the brief; ensure this is documented as an intentional deviation in the parity manifest, and that its yt-dlp fallback-per-`YoutubeCollectionKind` behavior is deliberate rather than an oversight.

## 3. Missing functionality

### SEARCH-M-01 — P1 — SoundCloud search extraction (tracks/playlists/users) not implemented in Rust
- Python: `apricot/search/search.py:451-474` (`soundcloud_search_entries`, using yt-dlp's `SoundcloudSearch` extractor with `search/playlists_without_albums` / `search/users` API endpoints and `scsearch{limit}:` for tracks), `apricot/search/search.py:703-729` (`open_soundcloud_artist_tracks`).
- Rust: not present. `grep -rli soundcloud` across `crates/` only turns up the unused `MediaSource::Soundcloud` enum variant (`apricot-core/src/media.rs:17,147`) and references in `main_menu.rs`, `navigation.rs`, `screen.rs`, `legacy_media.rs` (likely for migrating old library/favorites data, not live search). No `apricot-platform`/`apricot-media` code performs a SoundCloud search or user/tracks pagination. Note `context_menu.rs:18` does reserve a `"soundcloud_artist_tracks"` screen id in the `CONTEXT_MENUS` catalog, suggesting this was planned but not built.
- Notes: This is the single largest gap in the "search and online sources" area — SoundCloud is a first-class, always-visible provider in Python's search screen and is completely unreachable in Rust.

### SEARCH-M-02 — P1 — `open_channel` action unreachable from Search/Results screen (shortcut and context-menu item both missing)
- Python: `apricot/search/search.py:233-234` (`elif self.shortcut_matches(event, "open_channel"): self.open_item_channel(self.selected_result())`), plus conditional context-menu entry (`apricot/ui/menus.py:448`).
- Rust: Already flagged by a previous audit pass as missing from `activate_action()` in `win32.rs` (see `audit-SHELL.md`); this audit additionally confirms the context-menu route (SEARCH-06) is also missing, so there is currently **no** way to jump from a search/trending/channel-tab video row to its uploading channel in the Rust UI.
- Notes: Cross-referenced with the known Rust bug in `win32.rs`'s `activate_action()`; recorded here because it directly affects this audit's scope (Search/Results screen keyboard and context-menu parity).

### SEARCH-M-03 — P2 — "Copy stream URL" via `copy_direct_stream_url` uses selected item snapshot in Python but general active-item resolution in Rust (needs runtime check)
- Python: `apricot/ui/menus.py:444` — `lambda selected=dict(item or {}): self.copy_direct_stream_url(selected)` captures the exact selected result dict at menu-open time.
- Rust: `ID_CONTEXT_COPY_STREAM_URL => copy_active_stream_url(window)` (`win32.rs:1863`) re-resolves the "active" item at execution time via `active_media_item(window)`.
- Notes: Likely behaviourally identical in the common case (selection doesn't change between opening and choosing the menu item, since the menu is modal), but flagged because the mechanism differs (snapshot vs. re-fetch) and could diverge if selection changes are possible during a modal popup menu. Needs runtime verification rather than being a confirmed bug.

### SEARCH-M-04 — P2 — YouTube Shorts interleaving into "All"/"Video" search results not implemented
- Python: `apricot/search/search.py:410-449` — for search types `All`/`Video`, Python launches a parallel background fetch of a dedicated Shorts search URL (`youtube_shorts_search_url`, `sp=EgIQCQ==`) and interleaves up to 1 short per 4 primary results via `interleave_youtube_results` (`search.py:374-408`), deduping by video id/url. Also used for channel "uploads" (`youtube_channel_upload_results`, `search.py:482-495`, fetching `.../videos` and `.../shorts` in parallel and interleaving).
- Rust: `crates/apricot-platform/src/ytdlp_youtube.rs:471-498` (`search_target`) builds a single query per search (`ytsearch{limit}:{query}` for `Video`, or a filtered `youtube.com/results?...&sp=...` URL for `Playlist`/`Channel`) with no second Shorts-specific request and no interleave step; `grep -rn "shorts|interleave"` across `apricot-platform`/`apricot-app`/`apricot-media` finds no matching logic (only unrelated channel-tab-suffix lists that include `/shorts` as a URL suffix, e.g. `ytdlp_youtube.rs:549`, `subscription_controller.rs:397`).
- Notes: Whether YouTube's own `ytsearch` results already include some Shorts inline (a YouTube search-results-page behavior) was not verified at runtime; Python's explicit parallel-fetch-and-interleave exists specifically because flat `ytsearch` extraction does not reliably surface Shorts. This is likely a real content gap (fewer/no Shorts in Video/All search and no Shorts mixed into channel "uploads" results) rather than a cosmetic one — flagged P2, needs runtime verification to quantify.

## 4. Verified as matching

- Dynamic pagination engine (`SearchSession` in `search_session.rs`): 20-item page growth, generation-based stale-result rejection, selection-preserving merge/dedupe — matches Python's `maybe_extend_results`/`fetch_more_dynamic_results`/`merge_dynamic_results` semantics (`search.py:732-859`) including unlimited dynamic growth when the configured limit is 0 (`DYNAMIC_RESULTS_MAX = 0`, `constants.py:300`).
- Trending screen: initial focus goes to the country choice control in both (`search.py`'s Python equivalent `misc.py:1185` `focus_later(self.trending_country_choice)` vs. Rust `win32.rs:3891`-area `SetFocus(Some(state.trending_country))`); country/category persistence and "load_trending" auto-load-on-open both match.
- Channel tab order and URL construction: Python's `show_channel_options` dialog order (videos, playlists, streams, popular) and `channel_tab_url()` mapping (`popular`→`/videos`, `playlists`→`/playlists`, `streams`→`/streams`, default→`/videos`) matches Rust's `show_channel_options` dialog choice order and `ytdlp_youtube.rs:557-559` URL-suffix mapping.
- "Popular" sort key: Python's `popular_result_sort_key` (view_count desc, then recency, then title) matches Rust's `sort_popular_items`/`popular_numeric_value("view_count")`/`popular_recency_value` (`ytdlp_youtube.rs:577-599`).
- Direct-link Enter-key action dispatch: Python's `activate_direct_link_enter_action` (`system.py:227-236`) and Rust's `submit_primary_text`/`activate_direct_link` (`win32.rs:6702-6742`) use identical action strings (`play`, `download_audio`, `download_video`, `copy_stream_url`) and identical default (`play`).
- Result metadata hydration exists in Rust (`start_result_metadata_hydration`, `win32.rs:9396`, called after every results/collection render) with generation-scoped `apply_metadata`, matching the shape of Python's `start_result_metadata_hydration`/`result_metadata_worker` (`lists.py:479-520`) — batches videos lacking `view_count`/timestamp for hydration.
- Video result row text format (non-playlist/channel) matches Python field-for-field: title | Channel: x | Views: x | age | duration | type (`result_label`, `win32.rs:10372-10390` vs. `result_line`, `lists.py:636-643`).

## 5. Needs runtime/NVDA verification

- SEARCH-M-03 (copy-stream-url snapshot vs. re-resolve) — needs interactive check of whether selection can change while the results context menu is open (unlikely given native popup-menu modality on Win32, but not proven from source alone).
- Whether NVDA actually announces the "Copy link" vs. "Copy URL" difference (SEARCH-03) audibly differently, or whether NVDA's own caching could mask it — expected to be audible but not run interactively.
- Metadata-hydration announcement behavior (whether a row's text updating live without focus movement is silently absorbed by NVDA vs. announced) was not verified interactively in either build; Python explicitly defers updates to the currently-focused row (`result_line_update_should_defer`, `lists.py:874-889`) and Rust has an analogous `refresh_youtube_result_line` (`win32.rs:9623`) — the exact deferral condition text-diff was not exhaustively compared line-by-line for every intermediate state and would benefit from a live NVDA pass.
- SEARCH-M-04 (Shorts interleaving) — confirmed absent from source; the open question is purely how much this is masked by YouTube's own search results page already mixing in some Shorts, which needs a live A/B search comparison to quantify impact.
